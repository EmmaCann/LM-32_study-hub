# PROGETTO: LM-32 STUDY HUB

Sei un senior full-stack engineer specializzato in Next.js, TypeScript, UI/UX, sicurezza delle applicazioni web e architetture per la gestione di contenuti didattici.

Devi realizzare una piattaforma web universitaria privata, denominata **LM-32 Study Hub**, destinata a una studentessa della laurea magistrale in Ingegneria Informatica.

L'obiettivo è creare un ambiente personale, moderno, ordinato e responsive per consultare appunti universitari, animazioni interattive, simulazioni, esempi di codice, esercizi e PDF.

**Non limitarti a produrre documentazione o un mockup: implementa realmente il progetto, esegui i controlli disponibili e lascia una prima versione funzionante in locale.**

La piattaforma dovrà essere predisposta per integrarsi con skill di Codex CLI che svilupperemo separatamente.

# 3. SICUREZZA E ACCESSO PRIVATO

La piattaforma sarà destinata esclusivamente alla proprietaria.

La destinazione prevista per il deployment è Vercel, con:

**Vercel Authentication → All Deployments**

Questo deve proteggere anche il dominio di produzione.

Verifica la documentazione corrente di Vercel prima di predisporre la configurazione.

Per la prima versione:

- Non implementare un sistema di autenticazione personalizzato.
- Non creare credenziali predefinite.
- Non memorizzare password nel repository.
- Non implementare login fittizi spacciandoli per sicuri.
- Non introdurre pagine pubbliche contenenti contenuti universitari.
- Non pubblicare il progetto automaticamente.
- Non creare repository GitHub pubblici.
- Non caricare slide, trascrizioni, registrazioni o annotazioni originali.
- Non esporre informazioni sensibili in log, bundle client o variabili pubbliche.

La sicurezza del sito pubblicato dovrà dipendere dalla protezione di Vercel, ma il codice deve comunque seguire normali pratiche di sicurezza web.

Prevedi nel README una procedura per:

1. Pubblicare il progetto su Vercel.
2. Attivare Vercel Authentication su **All Deployments**.
3. Verificare che il dominio di produzione non sia pubblico.
4. Verificare che anche gli asset PDF/HTML siano protetti.
5. Provare l'accesso in navigazione anonima.
6. Accedere da Safari su iPad.

**Non effettuare un deployment reale né collegare account esterni senza autorizzazione esplicita.**

# 11. SISTEMA DI IMPORTAZIONE DEI CONTENUTI

Questa è una delle parti architetturali più importanti.

Le future skill Codex dovranno poter generare contenuti autonomamente, senza dover modificare manualmente la piattaforma.

Realizza quindi un sistema di importazione basato su file strutturati.

Definisci uno schema versionato, per esempio:

- `manifest.json` per i metadati.
- `content.mdx` per il contenuto didattico.
- `assets/` per immagini, diagrammi e PDF.
- `exercises.json` per gli esercizi.
- `simulations.json` per i riferimenti alle simulazioni.

La struttura precisa può essere migliorata se esiste una soluzione tecnica più robusta.

Requisiti:

1. Validazione dei file importati.
2. Validazione degli identificatori.
3. Rilevamento di duplicati.
4. Verifica dei riferimenti agli asset.
5. Aggiornamento di capitoli esistenti mantenendo gli URL.
6. Nessuna sovrascrittura distruttiva non necessaria.
7. Messaggi di errore comprensibili.
8. Possibilità di generare un'anteprima prima della pubblicazione.
9. Nessuna pubblicazione automatica di file non approvati.
10. Documentazione precisa per le skill che produrranno i contenuti.

Utilizza eventualmente Zod per validare i metadati.

Prevedi una directory di staging separata dai contenuti approvati.

I contenuti ancora da verificare non devono comparire nella versione pubblicata.

Gli import devono avvenire durante lo sviluppo/build o attraverso uno script controllato, non mediante endpoint pubblici di upload.
